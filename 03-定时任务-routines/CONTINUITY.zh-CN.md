# 连续性机制

本实验必须能应对上下文丢失、定时任务延迟启动、前一次运行中断等情况。本地项目文件是唯一可信的连续性来源。

## 每次启动流程

每个定时任务开始时，必须先读取：

- `AGENTS.md`
- `AGENTS.zh-CN.md`
- `02-项目文档-docs/TRADING-STRATEGY.md`
- `02-项目文档-docs/TRADING-STRATEGY.zh-CN.md`
- `03-定时任务-routines/schedule.json`
- `03-定时任务-routines/schedule.zh-CN.json`
- `03-定时任务-routines/CONTINUITY.md`
- `03-定时任务-routines/CONTINUITY.zh-CN.md`
- `04-运行状态-state/readiness.json`
- `05-交易记录-data/current-state.json`
- `05-交易记录-data/运行日志-journal/` 中最新记录，如果存在

做任何交易判断前，必须检查：

- paper trading 已启用。
- live trading 已关闭。
- 券商/API状态为只读，或已明确验证可用于 paper trading。
- 仓位、每日亏损和单笔亏损限制存在。
- 没有需要先核对的未完成前序任务。
- 新开模拟仓位前，必须通过无密钥公共五分钟成交量和推导 VWAP 检查，记录数据局限，并使用 Binance 报价作为模拟成交价格。

如果任何项目缺失、格式错误、过期、矛盾或不安全，只能观察，不能下单。

本机 launchd 兜底可能在 GPT 任务启动前已经完成同一时点的只读检查。此时
`duplicate_skipped` 表示只读证据已经存在，GPT 任务仍必须继续研究、写 paper 决策、日志和中文日报，不能把整个任务直接跳过。

## 每次结束流程

每个定时任务结束时必须更新：

- `05-交易记录-data/current-state.json`
- `05-交易记录-data/运行日志-journal/` 中当天交易日志
- `05-交易记录-data/证据资料-evidence/` 中的证据说明
- `09-每日中文报告-daily-reports/` 中当天的中文交易日报

中文日报必须明确写出买入或未买入原因、卖出或未卖出原因、缺失或延迟的任务、数据缺口、当日复盘和建议共同修改项。主动不交易与任务未运行必须分开记录。

收盘中文日报还必须分析当日美股大行情：主要指数表现、利率与油价、核心驱动、板块或风格结构、这些变化对当天决策的意义、下一交易日风险，以及可点击的来源链接。

## 日志必须包含

每条日志必须包括：

- 时间戳和定时任务 id
- 本次做了什么
- 为什么这么做
- 有没有提出订单
- 有没有提交订单
- 有没有成交
- 当前持仓
- 当前现金
- 当前风险
- 保存了哪些证据
- 下一次任务重点
- 是否需要人工确认

## 证据规则

证据文件不得包含凭证或密钥。证据应包含链接、来源名称、时间戳、市场数据快照，以及该证据如何影响决策的简短说明。

## 重复或中断的运行

如果发现前一次运行未完成：

- 不打开新风险。
- 先核对 current-state、journal 和任何账户读取结果。
- 记录中断情况。
- 只有状态一致后才恢复正常流程。

## 实盘边界

即使本地存在 API 凭证，实盘订单仍然禁止。只有用户在聊天中明确确认某一笔具体实盘订单，才允许继续。一般性的权限、API访问或账户资金不等于实盘授权。

## 已实现的只读恢复

在项目目录运行 `python3 -B 06-程序脚本-scripts/run_observation.py` 处理到期时点，或用 `--manual` 显式检查。进程锁限制并发，SQLite 用日期和时点组成唯一编号，遇到未完成运行则阻塞新运行。`--recover` 获取同一把锁后恢复已完成导出，并将中断的只读运行标记为 interrupted。它不会重发订单或回滚持仓现金。

API 检查日志和证据由 `05-交易记录-data/runs.sqlite3` 确定性导出，请勿手工编辑；研究内容单独写入带 `-research` 后缀的文件。`05-交易记录-data/current-state.json` 保存当前模拟组合，`05-交易记录-data/paper-ledger.json` 保存本地模拟成交事件。最近一次只读运行元数据可从数据库恢复。

每项股票检查记录自己的时间。一次新的 API 测试不会刷新地区资格、行情新鲜度或交易授权。5 秒采样、15 秒断线阈值仍属于待审阅的止损草案。
